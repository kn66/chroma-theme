* Chroma Theme

Chroma Theme is a color theme that preserves the design of Emacs's standard faces as much as possible while replacing only their color layer.

Whereas conventional themes redesign entire faces, including their font, weight, underline, box, and inheritance, Chroma owns only the decision of which semantic color each face should use. Its authored face mappings contain only ~:foreground~ and ~:background~ replacements.

** Design

Colors are separated into three layers:

#+begin_src text
Finite palette
    ↓
Semantic color roles
    ↓
Emacs face mappings
#+end_src

- The palette is a finite set of HEX values selected in advance by the author. Chroma does not calculate hue, lightness, saturation, or contrast at runtime to generate or adjust colors.
- Semantic roles describe how colors are used, with names such as ~bg-main~, ~fg-dim~, ~primary~, ~secondary~, ~error~, and ~match~.
- Face mappings contain only associations such as ~font-lock-keyword-face → primary-vivid~; they know nothing about HEX values.

The data structure is ~variant → display class → palette~. Chroma currently includes independent true-color palettes for the dark and light variants. Future 256-color and 16-color palettes can be added independently of the existing mappings.

** Primary and Secondary

Primary is the central color chosen by the user. When Secondary is set to ~auto~, Chroma selects it from combinations defined and verified by the author.

#+begin_src elisp
(setq chroma-primary 'blue)
(setq chroma-secondary 'auto) ; Select yellow for blue
(setq chroma-variant 'dark)
#+end_src

Secondary can also be overridden explicitly.

#+begin_src elisp
(setq chroma-primary 'blue)
(setq chroma-secondary 'orange)
#+end_src

The following ten hues are available:

- ~blue~
- ~azure~
- ~cyan~
- ~green~
- ~chartreuse~
- ~yellow~
- ~orange~
- ~red~
- ~magenta~
- ~purple~

The automatic pairings form five symmetric complementary axes in OKLCH:

| Color      | Angle | Complement | Angle |
|------------+-------+------------+-------|
| red        |   20° | cyan       |  200° |
| orange     |   60° | azure      |  240° |
| yellow     |   90° | blue       |  270° |
| chartreuse |  120° | purple     |  300° |
| green      |  150° | magenta    |  330° |

Automatic selection is reciprocal: applying it twice returns to the original hue. The canonical angles and pairings are defined in ~chroma-hue-angles~ and ~chroma-primary-secondary-pairs~ in [[chroma-palette.el][chroma-palette.el]]. Every chromatic finite palette leaf targets its canonical angle; nearly achromatic leaves retain their neutral source color, where a hue angle has no perceptual meaning. Literal 8-bit HEX values use the closest representable color to the exact OKLCH target.

Ordinary tones retain the source-relative OKLab lightness and chroma, reducing chroma only where the canonical hue would otherwise leave sRGB. For status and Diff indicator tones with narrowly defined contrast levels, the finite palette holds the source WCAG relative luminance fixed and selects the closest in-gamut lightness and chroma on the canonical hue axis. This prevents the 180° hue change from altering their effective contrast.

*** All chromatic roles follow the two selected colors

Chroma does not assign fixed red, yellow, green, or cyan colors to error, warning, success, and info. Every chromatic role—including those used for diffs, compilation, search, strings, and diagnostics—uses only Primary or Secondary and their finite tones. Neutral roles such as backgrounds, body text, and borders remain achromatic.

| Semantic family      | Selected hue         |
|----------------------+----------------------|
| error, removed       | Primary              |
| info                 | Primary emphasis     |
| success, added       | Secondary            |
| warning              | Secondary base       |
| changed indicator    | Secondary emphasis   |
| refined changed area | Secondary source-relative fine tone |

For example, when Primary is ~blue~ and Secondary is ~orange~, removed diff content is blue, added content is orange, and changed indicators and refined changed areas use orange tones. The standard ~diff-changed~ face has no distinct color of its own, so Chroma does not add one.

*** Tones that preserve the visual hierarchy of the original faces

Even when faces use the same hue, Chroma does not collapse their original lightness, background contrast, and degree of emphasis into a single color. The chromatic palette provides the following finite tones for different purposes:

| Tone                                 | Purpose                                                          |
|--------------------------------------+------------------------------------------------------------------|
| ~muted~                              | A regular, subtle background                                     |
| ~selection~ / ~standalone-selection~ | The region and an independent secondary selection                |
| ~refinement~                          | The standard general-purpose highlight background               |
| ~paren-match~ / ~pulse~               | Source-relative matching-parenthesis and transient highlights    |
| ~diff-*~ / ~fine-*~ / ~current-*~     | Diff, Magit, Smerge, and Ediff levels kept distinct              |
| ~alert~                              | Strong warning backgrounds such as trailing whitespace           |
| ~indicator-*~                        | The original low, middle, and changed Diff indicator levels      |
| ~status-*~                           | Variant-specific Error, Warning, and Success prominence          |
| ~ansi-*~                             | The original lightness ordering of normal and bright ANSI colors |
| ~base~ / ~emphasis~ / ~vivid~        | Regular, emphasized, and especially bright syntax text           |
| ~polarity-*~ / ~dark-only~           | Faces whose standard lightness changes between dark and light    |

The target lightness values for these tones are fixed in advance for both dark and light variants. Source-relative background tones preserve both the OKLab lightness and chroma of the corresponding standard face. Only when the selected hue would fall outside sRGB at that lightness and chroma does the finite palette reduce chroma while retaining lightness. Separate tones prevent a subtle Magit current hunk, a strong refined Diff region, and a brief Pulse highlight from collapsing into one saturation level. Dedicated neutral tones also preserve the original light–dark relationships of whitespace markers, mode lines, tabs, and window dividers.

** Installation and Configuration

A local checkout can be used with only the ~:load-path~ setting in ~use-package~. When ~chroma-theme.el~ is loaded, it also adds its directory to ~custom-theme-load-path~, making ~chroma~ available in the ~M-x load-theme~ list.

#+begin_src elisp
(use-package chroma-theme
  :load-path "/path/to/chroma-theme/"
  :custom
  (chroma-variant 'dark)
  (chroma-primary 'blue)
  (chroma-secondary 'auto))
#+end_src

You can then select it from the list or enable it in your configuration.

#+begin_src elisp
(use-package chroma-theme
  :load-path "/path/to/chroma-theme/"
  :custom
  (chroma-variant 'light)
  (chroma-primary 'blue)
  (chroma-secondary 'auto)
  :config
  (load-theme 'chroma t))
#+end_src

Without ~use-package~, add the directory to the regular load path and load the library once.

#+begin_src elisp
(add-to-list 'load-path "/path/to/chroma-theme/")
(require 'chroma-theme)
#+end_src

When Chroma is installed as a package, the generated autoload also registers the theme directory.

You can also use ~setq~ in the ~:config~ section of ~use-package~. Chroma rebuilds its face specs from the current options when the theme is enabled.

#+begin_src elisp
(use-package chroma-theme
  :load-path "/path/to/chroma-theme/"
  :config
  (setq chroma-variant 'light
        chroma-primary 'yellow))
#+end_src

** Dark / Light

Use ~chroma-variant~ to choose between independently designed and verified dark and light palettes. The light palette is not generated by transforming the dark colors at runtime.

#+begin_src elisp
(setq chroma-variant 'light)
(load-theme 'chroma t)
#+end_src

To switch variants after enabling the theme, reapply it as you would after changing any other option.

#+begin_src elisp
(setq chroma-variant 'dark)
(chroma-theme-refresh)
#+end_src

In Customize, use ~M-x customize-group RET chroma~ to select Dark or Light. Changes are applied automatically.

If you change colors with ~setq~ after enabling the theme, reapply it.

#+begin_src elisp
(setq chroma-primary 'red
      chroma-secondary 'auto)
(chroma-theme-refresh)
#+end_src

You can also make changes through ~M-x customize-group RET chroma~. Changes made through Customize are automatically reapplied to an active Chroma theme.

** Respecting Emacs's Standard Design

Chroma's authored mappings do not replace non-color information such as:

- family, foundry, height, and width
- weight and slant
- the presence or shape of underline, overline, and strike-through
- box geometry and line width
- extend, stipple, and inverse-video

Emacs normally treats a matching theme face spec as a complete replacement for that face's standard ~defface~ spec. Merely omitting structural attributes would therefore lose such properties as Org's inverse-video date selection, link underlines, and mode-line boxes.

To prevent that, each generated Chroma spec uses ~:inherit~ to reference a private proxy of the face's current upstream ~defface~ spec, then overrides only the mapped colors. These proxy specs are copied at runtime rather than hard-coded and are refreshed after libraries load, so changes in Emacs or a package remain authoritative.

*** Limitations of compound attributes

Values such as ~(:underline (:style wave :color "red"))~ and ~(:box (:line-width 1 :color "blue"))~ contain both structure and color in a single attribute. Emacs theme face specs cannot safely merge only the nested ~:color~; setting the entire attribute would fix the original style or geometry in place.

Chroma does not replace such compound attributes. The private upstream proxy retains them unchanged, so colors found only inside compound attributes, such as Flymake's wave underlines, remain as defined at their source. Any future recoloring support will be added only if a safe API or a narrowly scoped, verifiable method becomes available.

** Face Coverage

The initial release maps the major built-in faces in the following categories:

- Basic, Font Lock
- Mode Line, Header Line, Minibuffer
- Search, Match, Paren Matching
- Completion
- Fringe, Borders, Line Numbers, Tabs
- Diff, Ediff, Compilation diagnostics
- Dired, Help, Info, Calendar, Whitespace
- Gnus, Message, Smerge, EPA, ERT, EWW/SHR, Bookmark, Eshell
- Speedbar, TTY menu, Edmacro
- Explicit Org colors, Customize, Widget, ANSI color

Mapped faces are added to the theme spec only after a ~facep~ check, since availability varies by Emacs version and loaded libraries. If a built-in library defines new faces after the theme is enabled, a lightweight ~after-load-functions~ hook rebuilds the mappings and their upstream proxies.

The Emacs 30 built-in coverage is also checked in reverse: after the audited
libraries are loaded under a true-color display model, every face with a direct
simple foreground or background must have a Chroma mapping for exactly those
attributes.  This catches newly introduced or previously omitted direct colors
instead of validating only the mappings already listed by Chroma.

Faces that are chromatic in Emacs's standard true-color definitions are assigned to either Primary or Secondary. For example, ~region~, ~secondary-selection~, ~highlight~, Font Lock comments, and completion highlights retain color instead of becoming neutral, using finite tones of the two selected hues. Inherited faces such as ~hl-line~ receive the mapped color from their standard parent. Shadows and ordinary UI backgrounds, which are gray in the standard definitions, remain neutral roles.

Faces that have no distinct color in the standard definitions and only inherit another face do not have individual mappings. This includes Font Lock child faces, ~hl-line~, mode/header-line children, completion annotations, Compilation status children, Diff headers, and Dired's standard inherited faces. They receive Chroma colors from their respective standard parents. Chroma also does not add new chromatic colors to standard number, operator, punctuation, or regexp grouping faces that are colorless by default.

Because Primary is the theme's central color, it is preferentially assigned to the current line, ordinary emphasis, and major syntax elements. The ~region~ selection uses Secondary so it remains distinguishable when overlapping ~hl-line~. Secondary is also used for supporting meanings that should be differentiated from Primary, such as secondary selections, additions and success, and visited links. ERT verifies that Primary accounts for at least 55% of the chromatic attributes in the face mappings.

The standard Emacs face is named ~link-visited~, not ~visited-link~, so Chroma maps ~link-visited → visited-link~ as a semantic role.

*** External packages

Chroma supports the following external packages, whose defaults use specific colors:

- Avy 0.5.0
- Corfu 2.10 (including the ~corfu-popupinfo~ inheritance chain)
- diff-hl 1.10.0
- Magit / magit-section 4.6.0
- Tempel 1.14
- Transient 0.13.5
- Vundo 2.4.0

The listed versions are those whose face definitions were audited. Integration
tests read the actual ~defface~ forms from exact, commit-pinned upstream
checkouts and verify that every direct color is mapped, every inherited-only
face remains unmapped, and each private proxy matches the complete upstream
specification. Chroma does not ~require~ these packages as runtime dependencies.
If a package has already been loaded, Chroma sets only the faces that exist. If
a package is loaded after the theme is enabled, the additional faces are
applied through ~after-load-functions~.

For external packages, Chroma likewise maps only ~:foreground~ and ~:background~ where the upstream defaults specify concrete colors. The generated upstream proxy preserves properties such as Tempel's ~:slant~, Vundo's ~:weight~, and Magit Diff's ~:extend~. Mappings are not duplicated when a child face merely inherits a standard face or a package face that already has colors set.

When multiple lines are selected in Magit, the range boundary in
~magit-diff-lines-heading~ uses a source-relative Primary tone that retains the
upstream foreground/background contrast. Chroma does not set a color on
~magit-diff-hunk-region~, which overlaps the selected lines, preserving both
Magit's bold styling and the added/removed colors beneath it.

Packages designed primarily around standard face inheritance—such as Consult, Embark, Marginalia, Vertico, Which-key, and Denote—inherit Chroma's built-in face colors without individual mappings. Colors are not reduced to Primary and Secondary for packages where the range of colors itself carries information, such as Rainbow Delimiters or previews of colors in actual data.

External mappings are kept separately in [[chroma-faces-external.el][chroma-faces-external.el]] and use the same semantic roles and validation rules as the built-in mappings.

** Supported Environments

- Target Emacs version: 30.1 or later
- Development and verification environment: Emacs 30.2
- Officially supported display: GUI / true-color
- Supported variants: dark / light

Face specs apply only to color displays with at least 16,777,216 colors. Because Chroma does not include unverified approximations for 256-color or 16-color terminals, those environments are currently unsupported. Chroma's color specs are not applied in non-true-color environments.

** Palette and Contrast

Every color is specified explicitly in [[chroma-palette.el][chroma-palette.el]]. Runtime code performs palette lookups only.

For testing only, ERT calculates WCAG relative luminance and contrast ratios and verifies at least the following:

- Main text in dark and light variants: at least 7.0:1
- Representative normal text in dark and light variants: at least 4.5:1
- The base color against the main background for every hue in both variants: at least 4.5:1
- The emphasis color against the main background for every hue in both variants: at least 4.5:1
- Main text against muted highlight backgrounds for every hue in both variants: at least 4.5:1
- Status base/emphasis against the corresponding muted background for every hue in both variants: at least 4.5:1
- For every hue, refinement stands out from the background more than muted, and alert more than refinement
- Selection/refinement retains higher OKLab chroma than muted
- Vivid syntax falls within dark/light contrast ranges close to the standard faces
- The relative lightness ordering of Diff/Smerge refinement, window dividers, and mode/tab UI
- Every directly specified foreground/background pair across all 10 Primary
  hues, all 10 Secondary hues, and both variants stays within 0.12 of the
  upstream WCAG contrast ratio
- The same 200-combination pair check for the audited external-package faces

These calculations are used only to validate the palettes, not to generate or adjust colors at runtime.

** Development

#+begin_src sh
make test       # All ERT tests
make compile    # Byte-compile
make checkdoc   # Docstring/style checks
make clean-elc  # Remove generated .elc files
#+end_src

External-package integration tests use exact upstream revisions and are kept
separate from the dependency-free default test run.

#+begin_src sh
make bootstrap-external  # Clone and verify the pinned audit fixtures
make test-external       # Audit real external defface forms and color pairs
#+end_src

Tests are divided into palette, core, face-invariant, and contrast suites. For non-color information in particular, they verify that mappings contain only ~:foreground~ and ~:background~, that every built-in mapping replaces all and only colors explicitly set upstream, that generated specs inherit an exact runtime proxy of the upstream ~defface~, and that representative faces retain their effective structural attributes. Regression tests also cover duplicate external package face names, semantic roles, Primary's share of chromatic attributes, and the relative ordering of lightness, refinement, and boundaries found in the original faces.
